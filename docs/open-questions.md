| 12 | Session lifetime | Not in the spec. Chose 12 h absolute expiry on a DB-backed session token in an HttpOnly cookie (DB-backed, not JWT, so §3's account deactivation / password reset revokes immediately) | **Resolved (2026-07-30)**: **24 h as a sliding window** — every authenticated request (`app/auth/dependencies.py::current_session`) pushes both the server-side `UserSession.expires_at` and the cookie's `Max-Age` out to a fresh 24 h, rather than a fixed 24 h counted from login only. `GRADINGHELPER_SESSION_LIFETIME_HOURS` still controls the window length. Implemented in `app/auth/sessions.py::get_valid_session` (DB refresh) + new `app/auth/cookies.py` (cookie refresh, shared with login/logout). **Noted future improvement, not implemented**: pure sliding expiry has no hard ceiling — a replayed cookie stays valid indefinitely as long as it's used at least once per window. Common practice pairs sliding renewal with an absolute cap (e.g. never beyond N days from login regardless of activity). Deliberately not added now — not worth the complexity for an internal, admin-created-account tool — but worth adding if this is ever exposed more broadly |

| 16 | Charting library for the §9 interactive dashboard | §9 left it open: "Chart.js/Recharts/Plotly — pick one during implementation" | **Resolved (M4)**: **Recharts**. Pure SVG, so it needs no `canvas` polyfill under jsdom the way Chart.js would, and it is declarative React rather than an imperative instance to manage in an effect. Bundled by Vite, so no runtime CDN fetch (§13). Mitigation for its one real weakness under jsdom is structural: every payload→series transform is a pure tested function in `frontend/src/statistics/series.ts`, and every chart is accompanied by the same data as a `<table>`, which most tests assert against and which also prints. | 17 | Charts inside the §9 PDF: `cetz`/`cetz-plot` vs. native Typst drawing | §12 names `cetz` + `cetz-plot`, vendored into the image at build time (§13) | **Resolved (post-M4) — back to the spec's choice.** Initially deviated: bars were drawn with native Typst primitives behind one `bar-chart()` function, to avoid committing a third-party package tree ahead of §15.6. The user reviewed the output and rejected it — the hand-drawn bars ran left-to-right, inverting the axes, and looked poor. They also clarified the §13 constraint: it forbids ever **uploading** exam data, and a build-time download of a public package is fine. So `cetz` 0.3.4 + `cetz-plot` 0.1.1 are now fetched by `backend/scripts/vendor_typst_packages.py` (version- and SHA-256-pinned) into a gitignored tree, wired in through `typst-py`'s `package_path`, and the Dockerfile runs the same script at build time. Both packages are **LGPL-3.0** in an otherwise proprietary repo — hence downloaded rather than committed, with LICENSE files preserved in the image. Lesson worth keeping: the deviation was defensible on paper and still wrong in practice, because nobody looked at the rendered PDF until after it shipped |
| 18 | What §9's statistics mean while grading is still in progress | Not addressed by the spec, which only says §9 is "a live view over current data … useful while grading is still in progress" | **Decided (M4)**: a student who attended but is missing at least one exercise entry is counted as `incomplete` and left out of the grade distribution and the total-points histogram — their partial sum would otherwise render as a fake "nicht bestanden" — while their individually entered exercise points still count in that exercise's own histogram, where they are a complete fact. Pass and failure rates divide by `graded` (attended **and** complete), not by `attended`, or an in-progress exam would understate its failure rate. Both views must show the `incomplete` count prominently. Two refinements found while testing the seam: (a) a student recorded as **absent** whose points are still stored — a state `docs/api-contract.md` guarantees is reachable, since flipping `attended` to false deliberately keeps points so nobody re-transcribes an exam — is excluded from the per-exercise histograms too, because §7.4 makes those points play no part in any grade; a student whose attendance is merely *not yet recorded* still counts, since entering points before ticking attendance is an ordinary order to work in. (b) attended-and-complete students on an exam with **no grading schema yet** get their own `counts.awaiting_schema` bucket rather than falling into none, so the five buckets always partition `registered` — without it an instructor who configures the schema last watched students vanish from every count. Confirm the instructor reads all of this the same way once they use it on a real exam |
| 19 | Rounding of §9's derived numbers | Not specified | **Decided (M4)**: mean/median grade to 2 decimal places, rates to 1, both `ROUND_HALF_UP`, and **rounded once in `app/statistics.py`**, never in a renderer — §9's "one shared statistics module" requirement is defeated if the PDF and the dashboard round the same payload differently. For the same reason every rate travels as `numerator`/`denominator`/`percent` together so neither view divides, and histogram bin captions are formatted German-side in that module rather than twice in two renderers |

| 21 | Attendance input: two-state checkbox vs. preserving "not yet recorded" | Not in the spec. §4 makes `attended` nullable and §8.1 requires the export gate to distinguish "never recorded" from "did not appear" | **Decided (post-M4)**: a **radio pair** per student (anwesend / nicht anwesend), neither selected while `null`. | 22 | Does the §8.1 export gate for §10/§11 also need to block on the grading schema being configured, not just attendance/points completeness? | §8.1's own text only names attendance and exercise points; it doesn't mention the grading schema at all | **Decided (M5)**: yes — blocked. §10/§11 both require a "Note" per student, which is impossible to compute (`app/grading/engine.py::compute_grade` requires all ten §7.1 grades) with no or a partial schema, and §8.1's "never generate a report with... missing grades" reads as covering this case even though the literal checklist doesn't name it. `app/api/reports.py::_require_exportable` therefore checks `exam_completeness` (unchanged, still exactly §8.1's literal checklist) **and**, separately, that all ten grade thresholds exist, collecting both as German `409` errors rather than extending `exam_completeness` itself — keeps that shared helper's existing meaning and tests untouched. `PointsEntryPage.tsx`'s "Vollständigkeit" panel mirrors this: the four report-download buttons are gated on `completeness.is_complete && grid.grading_configured`, with a hint shown when only the schema is missing |

| 23 | `bonus_points` moved from `StudentRegistration` (one value per student) to `Exam` (one value for the whole exam) — §7.3/§4/§8 all originally described it as per-student | User request (post-M6): the professor sets one bonus amount for the whole exam, not per student | **Resolved (2026-08-03)**: `SPECIFICATION.md` §4/§7.3/§8/§8.1 updated to match. `app/models/exam.py::Exam.bonus_points` replaces `StudentRegistration.bonus_points` (migration `8ab4f293a4ce`); every `compute_grade`/`student_note`/`_classify` call site now reads the exam's value instead of the registration's. Not part of the §4 copy-forward list (it's entered data, not configuration — a new exam always starts at 0). Editing it after points exist now triggers the same §8.1 recomputation-warning mechanism as `exercises`/`grading_schema` (`app/api/exams.py::update_exam`), since it can move every non-excluded student's grade in one edit — the before/after grade snapshot must bracket the mutation, and forgetting `db.flush()` after assigning `exam.bonus_points` before the "after" snapshot's `db.expire_all()` silently made the warning report 0 changes even when grades genuinely moved (caught by `tests/test_points_api.py::test_worked_example_7_5_through_the_http_api`). Migration data step: per exam, carries forward the **highest** previously entered non-excluded student value (never `0` flatly and never an arbitrary "first") — safe because the points-entry UI already presented bonus as one field fanned out to every row before this change, so real per-exam data was already expected to be unanimous. Separately, and unrelated to the schema change itself: writing this migration surfaced that `app/db.py`'s process-global `PRAGMA foreign_keys=ON` listener defeats Alembic's own "turn FK off during a batch-mode table recreate" safety net on SQLite (the pragma can't change mid-transaction, and one is already open by the time batch mode tries), so any future migration that batch-alters a table with incoming `ondelete="CASCADE"` foreign keys — not just this one — would silently cascade-delete its children. Fixed once, for good, in `alembic/env.py::run_migrations_online` (`PRAGMA foreign_keys=OFF` before `context.begin_transaction()` opens anything) rather than worked around per-migration |
