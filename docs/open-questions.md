| 12 | Session lifetime | Not in the spec. | 18 | What §9's statistics mean while grading is still in progress | Not addressed by the spec, which only says §9 is "a live view over current data … useful while grading is still in progress" | **Decided (M4)**: a student who attended but is missing at least one exercise entry is counted as `incomplete` and left out of the grade distribution and the total-points histogram — their partial sum would otherwise render as a fake "nicht bestanden" — while their individually entered exercise points still count in that exercise's own histogram, where they are a complete fact. Pass and failure rates divide by `graded` (attended **and** complete), not by `attended`, or an in-progress exam would understate its failure rate. Both views must show the `incomplete` count prominently. Two refinements found while testing the seam: (a) a student recorded as **absent** whose points are still stored — a state `docs/api-contract.md` guarantees is reachable, since flipping `attended` to false deliberately keeps points so nobody re-transcribes an exam — is excluded from the per-exercise histograms too, because §7.4 makes those points play no part in any grade; a student whose attendance is merely *not yet recorded* still counts, since entering points before ticking attendance is an ordinary order to work in. (b) attended-and-complete students on an exam with **no grading schema yet** get their own `counts.awaiting_schema` bucket rather than falling into none, so the five buckets always partition `registered` — without it an instructor who configures the schema last watched students vanish from every count. Confirm the instructor reads all of this the same way once they use it on a real exam |
| 19 | Rounding of §9's derived numbers | Not specified | **Decided (M4)**: mean/median grade to 2 decimal places, rates to 1, both `ROUND_HALF_UP`, and **rounded once in `app/statistics.py`**, never in a renderer — §9's "one shared statistics module" requirement is defeated if the PDF and the dashboard round the same payload differently. | 23 | Invitation-code self-registration: expiry configurable per code, and can a code grant admin? | Not in the original §3, added by user request post-milestone-6 as a second way to create an instructor account alongside admin-direct-create | **Decided (2026-08-04)**: expiry is a **deployment-wide configured lifetime** (`GRADINGHELPER_INVITATION_LIFETIME_DAYS`, default 7 days), not a per-code field — the request said "a pre-defined amount of time," not an admin-tunable one, and it matches how `session_lifetime_hours` is already configured. A code **always** creates a non-admin account; there is no way to request admin rights through one, matching this app's existing least-privilege defaults (item 5). `app/api/admin.py` (issue/list/revoke, admin-only) and `app/api/auth.py::register` (the one unauthenticated redemption route, alongside `/login`). **Reversed same day**: initially shipped single-use (atomic `UPDATE ... WHERE used_at IS NULL AND revoked_at IS NULL` + `rowcount` check so two concurrent redemptions of the same code couldn't both succeed). The user's actual intent was one code posted once in a group chat for a whole team to use — single-use defeated that on first redemption. Now **reusable**: `InvitationCode.redemption_count` (incremented SQL-side, `redemption_count + 1`, not a Python read-modify-write, so concurrent redemptions still can't lose a count) replaces `used_at`/`used_by_id`; a code stops working only on `expires_at` or admin revocation, never on being used. Consequence worth restating: a leaked single-use code cost one account, a leaked reusable code is an open door until expiry/revoke — expiry and revoke are the only backstops now, so a code shouldn't be posted more widely than intended. **Extended (2026-08-04)**: added an optional per-code `max_uses` (`InvitationCode.max_uses`, migration `a2ef145b150f`, `null` = unlimited, the prior behaviour) so an admin can cap a code to a known head count instead of relying only on expiry/revocation. Set once at creation, no PATCH to edit it later — same "revoke and reissue" posture as everything else on this model. The redemption route's atomic `UPDATE ... WHERE` (`app/api/auth.py::register`) now also guards `max_uses IS NULL OR redemption_count < max_uses` in the same statement that increments the count, so two concurrent redemptions of an about-to-be-exhausted code can't both squeeze through past the cap. `status` gained a fourth value, `exhausted` (`redemption_count >= max_uses`), alongside `active`/`expired`/`revoked` |

| 23 | `bonus_points` moved from `StudentRegistration` (one value per student) to `Exam` (one value for the whole exam) — §7.3/§4/§8 all originally described it as per-student | User request (post-M6): the professor sets one bonus amount for the whole exam, not per student | **Resolved (2026-08-03)**: `SPECIFICATION.md` §4/§7.3/§8/§8.1 updated to match. `app/models/exam.py::Exam.bonus_points` replaces `StudentRegistration.bonus_points` (migration `8ab4f293a4ce`); every `compute_grade`/`student_note`/`_classify` call site now reads the exam's value instead of the registration's. Not part of the §4 copy-forward list (it's entered data, not configuration — a new exam always starts at 0). Editing it after points exist now triggers the same §8.1 recomputation-warning mechanism as `exercises`/`grading_schema` (`app/api/exams.py::update_exam`), since it can move every non-excluded student's grade in one edit — the before/after grade snapshot must bracket the mutation, and forgetting `db.flush()` after assigning `exam.bonus_points` before the "after" snapshot's `db.expire_all()` silently made the warning report 0 changes even when grades genuinely moved (caught by `tests/test_points_api.py::test_worked_example_7_5_through_the_http_api`). Migration data step: per exam, carries forward the **highest** previously entered non-excluded student value (never `0` flatly and never an arbitrary "first") — safe because the points-entry UI already presented bonus as one field fanned out to every row before this change, so real per-exam data was already expected to be unanimous. Separately, and unrelated to the schema change itself: writing this migration surfaced that `app/db.py`'s process-global `PRAGMA foreign_keys=ON` listener defeats Alembic's own "turn FK off during a batch-mode table recreate" safety net on SQLite (the pragma can't change mid-transaction, and one is already open by the time batch mode tries), so any future migration that batch-alters a table with incoming `ondelete="CASCADE"` foreign keys — not just this one — would silently cascade-delete its children. Fixed once, for good, in `alembic/env.py::run_migrations_online` (`PRAGMA foreign_keys=OFF` before `context.begin_transaction()` opens anything) rather than worked around per-migration |

| 24 | Whole-exam export/import: file format, what happens to `owner_id`, and what "no such lecture" means | Not in the spec at all — added by user request post-milestone-6: "export and import a whole exam (with student data and points) to/from a file... when importing an exam and there is no such lecture, automatically create it" | **Decided (2026-08-04)**: a single JSON file (`ExamExportPayload` in `app/api/schemas.py`), decimals as strings same as every other wire boundary (§7.0). Import always creates a **new** `Exam`, never a merge into an existing one — "import a whole exam" reads as a restore/transfer, not an upsert, and merging would need conflict rules the request never specified. `owner_id` is not part of the file at all: the importer always becomes the new exam's owner, so a file from another installation can't reference a meaningless (or someone else's) user id — an omission, not a round-trip gap, since re-exporting the imported copy just reflects the new owner like everything else does. Registration `points` are keyed by the exercise's 1-based index within the file's own `exercises` list rather than by `Exercise.position` or a database id, so the mapping survives even a hand-edited file whose positions are no longer contiguous. "No such lecture" is resolved by an **exact, case-sensitive name match against the importing instructor's own lectures only** — never another instructor's, even if same-named (same 404-not-403 posture as the rest of the API) — and a miss creates one, reported back as `lecture_created: true`. Lives in `app/api/exams.py` (routes `GET /exams/{id}/export`, `POST /exams/import`) rather than a separate module: it reuses that module's exercise/grading-schema validate-and-replace helpers directly rather than making them public for one extra caller. Excluded registrations are exported and re-imported like any other (§5.3: excluded is an audit flag, never a deletion) |
